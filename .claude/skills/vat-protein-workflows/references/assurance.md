# Approval and assurance checklist

Before proposing work:

- Confirm the selected adapter is implemented and not blocked.
- Keep one immutable generation and fixed evaluations; do not create an optimization campaign.
- State whether each tool is offline-ready, deployed or validated.
- Keep unavailable scientific values unavailable; do not invent affinity or safety scores.

Before execution:

- Display the complete canonical proposal and its digest.
- Obtain owner approval of that exact digest.
- Obtain a separate explicit spend authorization for deployment, image building or a Modal call.
- Stop if required source, model, database, license or image identities are not staged.

When reporting:

- Distinguish Python success, domain outcome, scientific acceptance and bundle verification.
- Call an offline test an offline test and a dry-run a dry-run.
- Describe signatures as local role-bound integrity, not independent notarization.
- Treat Claude Science's reviewer as a consistency review of recorded work, not independent
  execution or scientific replication.
- State that completeness is relative to the signed session and cannot rule out other sessions.
- Describe public Rekor inclusion as "this identity signed this receipt digest before this
  countersigned time"; never as notarization, execution time or proof that computation ran.
